# Описание проекта PetCare

**Дисциплина:** «Проектирование информационных систем»  
**Тип:** клиент-серверное веб-приложение  
**Версия:** 1.0

## 1. Предметная область и цель

Владельцам домашних животных нужно хранить сведения о питомцах и историю повседневного ухода: кормление, прогулки, гигиенические процедуры, вакцинации и наблюдения за здоровьем. При хранении информации в заметках и разрозненных приложениях сведения сложно быстро найти, а события разных питомцев могут смешиваться.

PetCare централизует каталог животных, личные карточки питомцев и дневник ухода. Клиент управляет только своими питомцами и записями. Администратор модерирует общий каталог и просматривает аудит действий.

**Цель:** разработать информационную систему с REST API, ролевым разграничением доступа, базой PostgreSQL, адаптивным интерфейсом и воспроизводимым развёртыванием.

Задачи проекта: реализовать CRUD, валидацию входных данных, регистрацию и JWT-вход, bcrypt-хеширование, проверку владельца, журнал аудита, автоматическую загрузку демонстрационных данных и документацию пользовательских историй.

## 2. Архитектура решения

Система состоит из трёх Docker-сервисов:

1. **Frontend / Nginx Alpine** — отдаёт HTML, CSS и JavaScript SPA; проксирует `/api/` к backend.
2. **Backend / FastAPI** — REST API, Pydantic-валидация, JWT-проверки, бизнес-логика и SQLAlchemy ORM.
3. **Database / PostgreSQL 15** — постоянное хранение пользователей, каталога, питомцев, дневника и аудита.

Поток запроса: браузер → Nginx → FastAPI router → проверка JWT/роли и владельца → SQLAlchemy → PostgreSQL → JSON-ответ → обновление SPA. База не публикуется наружу; backend доступен frontend внутри сети Docker Compose.

## 3. Сущности и ER-связи

**users**: `id` (PK), `username` (unique), `email` (unique), `password_hash`, `role` (`Client`/`Admin`), `created_at`.

**animals**: `id` (PK), `name`, `species`, `breed`, `description`, `care_tips`, `is_active`, `created_at`. Это общий справочник, доступный клиентам на чтение и администратору на изменение.

**pets**: `id` (PK), `owner_id` (FK → users.id), `name`, `species`, `breed`, `birth_date`, `weight_grams`, `notes`, `created_at`. Вес хранится целым числом граммов: 1300 означает 1,3 кг.

**care_entries**: `id` (PK), `pet_id` (FK → pets.id), `entry_type`, `title`, `details`, `entry_date`, `completed`, `created_at`.

**audit_logs**: `id` (PK), `actor_id`, `actor_username`, `action`, `entity_type`, `entity_id`, `details`, `created_at`. Логин пользователя сохраняется снимком для аудита; журнал доступен только Admin.

```text
users 1 ───── N pets 1 ───── N care_entries
  │
  └────────── N audit_logs (логическая связь по actor_id)
animals (общий каталог, отдельная сущность)
```

## 4. CRUD и матрица прав

| Сущность / действие | Client | Admin |
|---|---|---|
| Каталог: чтение активных записей | Да | Да |
| Каталог: создание/изменение/удаление | Нет | Да |
| Карточки питомцев: CRUD | Только свои | Только собственные в пользовательском API |
| Дневник: CRUD | Только записи своих питомцев | Только записи своих питомцев |
| Просмотр журнала аудита | Нет | Да |
| Регистрация | Да, роль Client назначается сервером | Через публичную регистрацию нельзя получить Admin |

CRUD каталога и карточек питомцев реализован полностью; дневник также поддерживает создание, чтение, изменение и удаление. Валидация Pydantic ограничивает длину строк, обязательные поля, допустимые типы записей, формат email и диапазон веса. Серверная проверка `owner_id` не позволяет получить доступ к чужим карточкам путём подмены ID.

Коды ошибок: `401` — недействительный токен, `403` — недостаточная роль, `404` — запись отсутствует или недоступна, `409` — конфликт логина/email, `422` — ошибка валидации.

## 5. Авторизация и аудит

При входе API выдаёт JWT с ID пользователя, логином, ролью и временем истечения. Пароль хранится только в виде bcrypt-хеша. Публичная регистрация всегда создаёт роль `Client`; административная роль задана только начальной демонстрационной учётной записи или доверенным администратором БД.

Аудит фиксирует регистрацию, вход, создание, изменение и удаление каталога, карточек питомцев и записей дневника. Панель администратора показывает пользователя, тип операции, сущность, ID и время события.

При первом запуске создаются таблицы, пользователи `client / client123`, `admin / admin123` и шесть демонстрационных записей каталога. Инициализация не дублирует существующие учётные записи и не заполняет каталог повторно, если он уже непустой.

## 6. Локальное развёртывание

Требуются Docker Engine и Docker Compose v2.

1. Скопировать `.env.example` в `.env`.
2. Перед использованием вне учебной демонстрации заменить `SECRET_KEY` и `POSTGRES_PASSWORD`.
3. Запустить `docker compose up --build -d`.
4. Открыть `http://localhost:3000`.
5. Проверить контейнеры командой `docker compose ps`; журналы — `docker compose logs -f backend`.
6. Остановить `docker compose down`. Удалить демонстрационные данные вместе с volume можно командой `docker compose down -v`.

Frontend доступен на порту 3000. Backend работает на 8000 внутри Docker-сети; для Swagger с хоста временно добавьте `ports: ["8000:8000"]` к backend, затем откройте `http://localhost:8000/docs`. Health-check API: `/api/health`.

## 7. Ограничения и развитие

Проект предназначен для учебной сдачи. Для production следует добавить HTTPS, rate limiting, миграции Alembic, автоматические тесты, резервное копирование, подтверждение email, сброс пароля, политику хранения аудита и пагинацию больших списков.
